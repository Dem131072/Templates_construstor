Прототип веб-приложения, предназначенного для упрощения заполнения типовых форм документов формата docx. 
Включает в себя функциональность конструктора шаблонов, где части текста заменяются на плейсхолдеры, и заполнителя шаблонов, 
который заменяет эти плейсхолдеры на пользовательский текст и опционально преобразует его в соответствии с типом и форматом.

Текущая архитектура прототипа:
.
├── doc_template_app         # бэкенд приложения
├── templates/               # HTML-шаблоны
├── static/                  # статические файлы фронтенда
├── doc_templates/           # сохраненные DOCX-шаблоны
├── saved/                   # заполненные DOCX-документы
└── custom_types.json        # пользовательские типы полей


Основной поток данных организован следующим образом:

1. В /constructor происходит загрузка docx-файла из файловой системы;

2. Извлечение word/document.xml из docx-архива;

3. XML документа преобразуется в HTML-предпросмотр: при выделении фрагментов текста появляется плавающая кнопка "Создать поле", 
которая открывает модальное окно создания плейсхолдера, позволяющее задать его параметры. 
Базовый формат плейсхолдера - {{name:type:format}},
где name - название, отображаемое пользователю,
type - тип поля,
format - опциональный формат для некоторых типов.
Например, при заполнении {{дата:date:full}} датой '11.11.2025'
плейсхолдер будет заменен на '"11" ноября 2025 г.',
тогда как без формата full он будет заменен на '11.11.2025'.

4. Формируются замены, включающие старые и новые значения текста, а также их расположение.

5. После подтверждения сохранения замены применяются к word/document.xml, и новый docx-шаблон сохраняется в выбранную папку. 
При сохранении возможен выбор директории сохранения шаблонов - возможно сохранение в /doc_templates или в одноуровневую подпапку в нем.

На базовой странице конструктора присутствует опция "Пользовательские типы текстовых данных", 
через которую реализуется создание и управление именнованными списками, что обеспечивает ускорение заполнения полей, 
требующих ввода ограниченного набора текстовых вариантов, например, адресов, помещений, должностей, организаций и т.д., 
за счет их удобного графического представления уже на странице заполнения, при этом такое поле сохраняет функциональность обычного поля text. 
Созданные пользователем шаблоны будут отображаться в модальном окне создания/редактирования плейсхолдера.

6. На главной странице отображаются файлы /doc_templates и его подпапок. При выборе "Заполнить" переход на заполнение.

7. Так же сканируется word/document.xml, плейсхолдеры извлекаются и отображаются в виде полей для заполнения. 
Построение полей формы происходит для каждого уникального значения плейсхолдера, несколько одинаковых плейсхолдеров отображаются одним полем.

8. Введенные значения при сохранении форматируются в зависимости от типа и формата.

9. При попытке сохранения при наличии незаполненных полей выводится предупреждение с подтверждением сохранения. 

10. При подтверждении плейсхолдеры заменяются на готовый текст, заполненный шаблон сохраняется в и происходит редирект на /history, 
где отображены сохраненные документы в /saved.


Работа заменами в самом файле docx осуществляется на уровне xml-узлов затронутых параграфов:

docx-файл открывается, как zip -> 
извлекается word/document.xml -> 
извлекаются текстовые узлы по параграфам -> 
производится перезапись в соответствии с параметрами расположения и содержания заменяемого текста ->
создается новый документ с измененным word/document.xml, при этом все остальные файлы архива копируются.


Сложность замены обусловлена спецификой текстовых узлов в docx-файлах.
Текстовые данные внутри xml параграфа часто хранятся подобным образом:

<w:p w:rsidR="00AA6BAF" w:rsidRPr="00A7789F" w:rsidRDefault="00AA6BAF" w:rsidP="00A7789F">
    <w:pPr>
        <w:spacing w:line="240" w:lineRule="atLeast"/>
        <w:jc w:val="center"/>
    </w:pPr>
    <w:r w:rsidRPr="00A7789F">
        <w:t>Наименование организ</w:t>
    </w:r>
    <w:r w:rsidRPr="00A7789F">
        <w:t>а</w:t>
    </w:r>
    <w:r w:rsidRPr="00A7789F">
        <w:t>ции, адрес.</w:t>
    </w:r>
</w:p>

То есть даже визуально и семантически единый текст может храниться в разных w:r.
Кроме того, разные документы могут по-разному кодировать стили и содержать разные простанства имен и служебные элементы, 
что создает дополнительные сложности при обеспечении совместимости между версиями Word/LibreOffice. 
Из-за этого для предупреждения автоматической записи xml в форматах, не поддерживаемых старыми версиями, 
не были использованы специализированные библиотеки для работы с docx, xml-атрибуты обрабатываются вручную.

Единицей обработки word/document.xml является параграф (<w:p>).
Внутри параграфа собираются текстовые узлы:

TextNode { run_idx: 0, text: "Наименование организ" },
TextNode { run_idx: 1, text: "а" },
TextNode { run_idx: 2, text: "ции, адрес." }

что позволяет построить план общего текста параграфа, включающего индекс TextNode 
и индекс символа внутри него, и создать структуру плана замены:

struct ReplacePlan { 
    start_run_idx: usize, // <w:r>, содержащий первый символ замены
    start_char_in_run: usize, // позиция начала в первом <w:r>
    end_run_idx: usize, // <w:r>, где замена заканчивается
    end_char_in_run: usize, // позиция конца в последнем <w:r>
    insert: String, // новый текст
}

Для каждого <w:r> строится список текстовых сегментов.
При разных расположениях текста по <w:r> замены обрабатываются по-разному:
Если замена внутри текущего <w:r>, то есть и начало, и конец в одном run'е, каждый сегмент затем будет записан как отдельный <w:r> с форматированием исходного.
Если замена начинается в текущем <w:r> и заканчивается в другом, удаляется остаток текущего <w:r>, последующие <w:r>, 
находящиеся внутри диапазона замены, будут очищены, при этом вставленный текст получает форматирование первого <w:r>, где началась замена.
Если текущий <w:r> полностью внутри диапазона замены, весь текст <w:r> пропускается.
Если замена заканчивается в текущем <w:r>, текст после конца замены будет сохранен.
При заполнении шаблона координаты для замен от фронтенда не нужны, 
поиск мест для замен, описывающего плейсхолдеры, осуществляется с помощью регулярного выражения.

Ограничения текущего прототипа:
Приложение является портируемым прототипом и хранит данные в фиксированных путях 
проекта в файловой системе без полноценной базы данных и авторизации/разделения пользователей.
Базовые ограничения безопасности, запуск предусмотрен только на 127.0.0.1.
HTML-предпросмотр позволяет просматривать только базовую структуру документа и плейсхолдеры в нем и не является полноценным WYSIWYG.
Допустимы только замены, не пересекающие несколько параграфов.
При замене сохраняется форматирование первого <w:r>, но не гарантируется полное сохранение всех сложных комбинаций разметки внутри заменяемого диапазона.
